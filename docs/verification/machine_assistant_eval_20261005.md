# 機況助手實驗驗證：能不能幫線上人員判斷硬體問題（2026-10-05）

> 問題：線上人員不懂硬體，只會說「看到什麼」。這套系統（一鍵健檢 + LoopEngineering 大模型 + 知識庫）能不能告訴他「哪裡壞、為什麼、該做什麼」？
> 方法：實驗室真的製造故障（每個都自動還原）→ 一鍵健檢收證據 → 用線上人員的原話問助手 → 逐題評分。
> 環境：Grab user-IMB-M47、Spark spark-c16f（+spark-3961 雙機跑 DeepSeek-V4-Flash）、HPE 5945（**廠商借用機；正式上線為 SN2201**）、6 × raL8192。

## 結論（給主管）

1. **一鍵健檢：7 個故障情境全部判對**（相機斷線、掉封包、參數被改、交換機上行斷、交換機重置、RDMA 線斷、Spark IP 程式停），
   每項都給出「哪一顆 CCD / 哪條線 / 哪台機器」、可能原因與現場步驟；全部故障都自動還原並複驗正常。
2. **助手只靠線上人員的描述（不按健檢）：9/20 分**——知識庫剛好有寫的（交換機 speed 1000）答得好；
   沒寫到的會往錯的方向猜，甚至給出有害建議（生產機 `gpu-reset`、查不相干的設定檔）。
3. **先按健檢再問助手：19/20 分**——助手能把報告翻成線上人員聽得懂的話、步驟正確。剩下 1 題扣分是建議刪 log（已加禁止事項）。
4. **所以現場流程定為：有問題先按 Control「一鍵健檢」→ 看結論；看不懂或要細節再開機況助手問**（健檢不需要大模型，生產中也能跑）。

## 實驗中找到並修好的問題（沒有實驗就不會發現）

| 問題 | 影響 | 修法 |
|---|---|---|
| 健檢把 RDMA CM 監聽當 TCP 查（`ss` 看不到 18515）| 健康時誤報「RDMA 埠沒在聽」| 改用 `rdma resource show cm_id` |
| 交換機 console（9600 鮑率）每次讀約 5% 行有亂碼 | 設定比對誤報 28 行差異；MAC 讀錯 1 字 | 設定讀 3/4 次取共識；MAC 表讀 3 次多數決、埠名須存在 |
| MAC 容錯比對（差 1 字也算）| **CCD05 被錯配成 CCD01**（同批相機 MAC 連號）| 拿掉模糊比對 |
| 相機「埠位基準」| 埠位會變（Addis 指正）| 改記 CCD↔MAC，只講 CCD 編號 |
| 5945 不支援入方向限速 | 掉封包情境沒注入成功（健檢「沒抓到」其實正確）| 改用最大框長；並把 jumbo 判斷寫進健檢 |
| 參考圖測圖用了 DEFAULT 配方 | 結果 0 顆（標準答案是 ini 預設參數跑的）| 不載配方、容許 ±2px（6/15 後演算法有修改，實得 5895 vs 5894）|
| 代理查 Loop 狀態逾時誤報「載入中」| 知識庫收錄時 Control 會顯示錯誤狀態 | 讀不到報 unknown、保守視為診斷模式 |
| 代理 POST 空內容被 Loop 拒收 | 機況助手開不起來 | 一律帶 JSON 內容 |
| Spark 7 天 105 筆 Xid | 看起來像 GPU 壞 | 健檢分類：程式類、來自開發測試程式 → 不影響生產 |

## 限制與待辦

- **光學偏暗（光源/鏡頭）無法在實驗室重現**（鏡頭收不到光，曝光 10000µs+最大增益亮度仍 2.9）→ 判斷邏輯以「和其他台比」+「參數是否被改」實作，待有光源時實測。
- **交換機部分只驗證 HPE 5945（借用機）**；正式 SN2201 指令與連線方式不同，到貨後補驅動並重跑本實驗。
- **助手 B 組的知識庫含實驗腳本本身**（fault_inject.py 有症狀↔故障對照）→ 「只給症狀 + 新知識庫」(A2) 分數受污染不採計；
  B 組主要證據來自健檢報告，影響較小。之後應把實驗腳本排除在收錄範圍外，用**新的、現場真實案例**重新考。
- 機況助手目前讀不到健檢報告，需線上人員貼上；LoopEngineering「遠端路徑」部署後可直接讀 `grab:/srv/cfaoi`（下一步：做成助手可呼叫的工具「跑健檢/讀最新報告」）。
- 健檢的取像測試在產線取像中會自動略過；GPU 深度檢查不影響生產 IP（另起離線 IP）。
