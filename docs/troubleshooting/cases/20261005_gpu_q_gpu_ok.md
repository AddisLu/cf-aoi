- 正確答案要點：見 docs/troubleshooting_線上異常處理.md 對應段落

## 機況助手表現（0–2 分）

- 問題 + 健檢報告（B）：**2** — 依 --gpu 報告：單元測試+參考圖正確 → GPU 沒壞，改查參數/批次/光源

<details><summary>助手 A 回答原文</summary>

## 結論

缺陷數暴增**不一定**是 GPU 壞了，請先檢查以下可能原因，不要直接判定硬體故障。

## 可能原因

根據知識庫中的 DEBUG 決策樹 [3]，缺陷數暴增（誤報太多）的可能原因依序為：

1. **閾值設定太緊** → 最常見，先從參數下手
2. **Pitch 設定錯誤** → pitch 設錯可能造成合併距離異常，導致缺陷數量爆衝（單 zone 約 5×10⁷ 次迭代，會把消費執行緒卡住秒級）[4][7]
3. **GPU 狀態異常** → 延遲過高或驅動問題

## 現場照做步驟（誰都可以做）

### Step 1：檢查 GPU 狀態（操作人員可做）
在 Spark（運算端）的 terminal 執行：
```bash
nvidia-smi
```
[1] → 確認 GPU 型號、記憶體用量、溫度是否正常、有沒有 process 在跑。

### Step 2：檢查延遲（操作人員可做）
查看檢測流程的延遲數據：
- 延遲 > 5ms → 降低 search_range 或關閉多尺度
- 延遲 > 10ms → 檢查 GPU 狀態或重新建置
- 延遲 > 50ms → GPU 故障或驅動程式問題 [3]

### Step 3：檢查 pitch 設定（工程師或操作人員可做）
確認 defect_rules.h 中的 `merge_distance` 參數是否設錯，pitch 設錯會導致合併邏輯跑出數萬顆缺陷（正常應為個位數～數百顆）[4][7]。

### Step 4：確認 CUDA 裝置（工程師可做）
若以上都正常，在 Spark 端跑驗證程式，檢查 `cudaGetDeviceCount()` 是否回傳 0 或錯誤 [2]。

## 如何確認修好

- 若 GPU 問題 → `nvidia-smi` 正常顯示 GPU、`cudaGetDeviceCount` ≥ 1、延遲回到 < 5ms，重新跑一塊 panel 缺陷數回到正常範圍
- 若 pitch 問題 → 修正後重新檢測同塊 panel，缺陷數應大幅下降
- 若閾值問題 → 調回原本數值後缺陷數正常

**結論：先看 nvidia-smi 和延遲，不要直接認定 GPU 壞了。**

<details><summary>助手 B 回答原文</summary>

**結論：目前「一鍵健檢」全部正常（3 項 OK），GPU 沒有壞。** 缺陷數突然變多的原因，知識庫中沒有找到直接對應的說法。

不過從健檢報告可以看到幾個有用資訊：

1. **GPU 運作正常** — NVIDIA GB10, 記憶體 112 GB, 溫度/功耗正常
2. **參考圖測圖結果正確** — 1 顆缺陷，類型與位置符合標準答案
3. **IP 離線單元測試 5 組全過**
4. **但最近 7 天有 105 筆 GPU 程式錯誤紀錄**（Xid 13、31、43），來自 `ccl_bench`、`dbg`

---

### 可能原因

| 可能原因 | 說明 |
|---|---|
| **檢測參數/門檻被改動**（最常見） | 如果 `default_zone.ini` 或各 zone 的亮度、對比、濾波參數被調鬆，會讓原本不會報的輕微灰階差異變成缺陷 [2] |
| **被測產品批次變更** | 板子表面顏色、鍍層、線寬有變化，同一套參數下缺陷數就會暴增 |
| **光源或相機穩定性** | 亮度波動導致同一位置時好時壞，GPU 本身沒壞 |
| **GPU 程式錯誤可能導致漏檢或誤報** | 105 筆 Xid 13/31/43 雖然目前沒造成當機，但若發生在檢測期間，可能造成 intermediate buffer 內容異常 [3] |

---

### 現場照做步驟（誰可以做）

1. **換一張已知良品板子測試**（產線人員）
   - 拿一片過去確認是 PASS 的板子，重新跑一次檢測
   - 如果缺陷數回到正常 → 前一批板子有問題
   - 如果還是很多 → 參數或機台問題

2. **按「一鍵健檢」重新跑一次**（產線人員）
   - 現在報告是 18:19 的，確認 GPU 參考圖測圖仍然正確
   - 如果健檢出現 FAIL，照健檢報告的「請這樣做」處理

3. **檢查 ip/config/default_zone.ini 是否有被修改**（軟體工程）
   - 比對備份檔或 Git 記錄，看 Filter、Threshold 等參數是否被調過 [2]

4. **重開 Spark 再測**（產線人員）
   - 先關閉 AOI 軟體，重新啟動 Spark 服務，再跑一次檢測
   - 如果恢復正常 → 暫存狀態異常

---

### 怎麼確認修好

- **良品板連續 PASS 3 片**，缺陷數與歷史平均值 ±20% 以內
- **一鍵健檢全部 OK**（GPU、取像、交換機、RDMA、相機）
- **同一片板子兩次檢測結果一致**（缺陷位置、數量、類型相符）

> 如果上述步驟都試過仍異常，請通知軟體工程調出 **IP04_Origin000027 的完整 DefectInfo JSON** [2][4] 比對演算法輸出，判斷是參數問題還是 GPU 計算錯誤。
